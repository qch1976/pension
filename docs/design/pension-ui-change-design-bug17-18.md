## 1. Bug17：Z实 2.4068 vs 用户逐年相加 2.4843

### 1.1 N应缴 / K 怎么算（精确代码位置）

文件 `calculator/pensionEngine.js`，主入口 `calculate(input)`：

```js
var windowStartIdx = insuredWindowStart(input);        // 第451行
var retireIdx = D.toIndex(input.retireYM);             // 第452行
var lastContribIdx = retireIdx - 1;                    // 第453行 缴费计到退休前一月
...
var K = lastContribIdx - windowStartIdx + 1;           // 第458行 应缴月数
...
var Z实 = sumZ / K;                                    // 第555行
var N应缴 = K / 12;                                    // 第557行
```

- 窗口起点 `insuredWindowStart(input)`（第 39 行起）：31 号文晚参保人员取批准参保月。本案 `doc31Eligible=true, enterpriseInsuredYM='2000-11'` → `windowStartIdx = toIndex('2000-11')`。
- 窗口终点 `lastContribIdx = retireIdx-1`：退休 2033-07 → 计到 **2033-06**。
- 索引换算 `D.toIndex(ym)=year*12+(month-1)`（`calculator/dateUtil.js`）。

**实算（当前服务器源码，node 直跑）**：

```
windowStartIdx = 2000*12+10 = 24010   (2000-11)
lastContribIdx = 2033*12+5  = 24401   (2033-06)
K = 24401-24010+1 = 392 月
N应缴 = 392/12 = 32.6667 年
```

逐月序列实跑首末：`monthlyDetails[0].ym='2000-11'`，`monthlyDetails[391].ym='2033-06'`，`length=392`。

**逐项排除（任务清单 ①）**：

- 窗口起点/终点 off-by：**无**。两端均含当月，392 = 期望的 2000-11~2033-06（手算：2000-11 到 2033-06 共 32 年 8 月 = 392）。
- 退休年按 12 月计入：**无**。退休年只计到 `retireIdx-1`，2033 恰为 6 月。
- 某年重复计入：**无**。月序列按索引连续，不重复。
- Bug14 改动引入分母变化：**K（月数分母）未被 Bug14 改动**；Bug14 只改年度账 `Z年` 的折算口径（`buildAnnualIndexLedger` 内 `sumMonthZ/windowMonths`）。
- “旧 12 月加权与新月均 Z年混算”：**主汇总无混算**（主汇总是纯 `Σ月z/K`）；但**年度账显示值**在 Bug14 后对边界年是月均、对整年是年均，二者量纲不同——这正是用户把 34 行直接相加产生误算的根源（见 §1.2）。

> 结论：**引擎真实分母 K=392、N应缴=32.6667，正确。** 用户“反算 N应缴=33.667（多 12 月）”是把自己的 81.1528 除以引擎 Z实得到的**推算假象**，不是引擎内部值。且该反算自身不严格闭合（见 §1.4），不能据此判定“多了 12 个月”。

### 1.2 用户“逐年 ΣZ年÷N应缴”算法是否成立（任务清单 ②）

**不成立。** Bug14 后年度账（`buildAnnualIndexLedger`，第 268 行起）对每个日历年：

```js
zYear = round4(sumMonthZ / windowMonths)   // 第 312 行附近
```

- 整年（windowMonths=12）：Z年 = 该年 12 个月 z 的平均 = 月均 = 年均（量纲一致，等价于旧 `Xn/C全年`）。
- **边界年 2000（windowMonths=2）、2033（windowMonths=6）：Z年是这 2 / 6 个月的月均指数，不再是年值。**

把 34 行 Z年直接相加，等于默认每行都占 12 个月权重；2000 行（2 月）与 2033 行（6 月）被错误地按整年计入，故和值虚高。

**正确勾稽恒等式**（Bug14-16 定稿已确立，本轮再验证）：

```
Σ_n ( Z年_n × windowMonths_n ) ÷ K = Z实
```

即“年表显示值”必须**按应缴月数加权**后才能除以月数 K；等价于主汇总的 `Σ月z/K`。

### 1.4 2.4068 vs 2.4075 的差异解释（任务点名核实）

- **2.4075（上轮记录）**：Bug14-16 定稿时配置——2026 年基数 **286488**（月均 35811）、分母表 2026 起 = **11937**（assumed，沿用 2025 官方值）。本轮用该配置复跑：raw Z实 = **2.407485 → 2.4075**，与上轮一致，上轮记录无误。
- **2.4068（用户当前所见）**：今日 12:08 之后、`policyData.js` 的 `indexDenominatorMonthly` 2026 键由 11937 改向 **12116**、且 2026 年缴费基数由 286488 改向 My-Case 的 **287562** 的**切换中间态**实跑值。分母上调使低指数段（未来 0.6 段、2026 混合段）占比变化，Z实由 2.4075 略降至 ~2.4068。
- **2.4050（本轮此刻服务器权威实跑）**：切换完成后（2026 年基 287562、2026 及 2027+ 分母均 12116）= 2.40495 → **2.4050**。

> 差异根因是**配置/基线漂移，不是算法或 K 错误**。旁证：本轮实跑 `autotest/output-assert.js` 已 **FAIL**——其断言基准仍写旧口径（期望 Z实 2.4075、2026 分母按 11937 派生的 2.2/0.6 等），与当前 policyData（12116）不一致。测试基准必须随锁定基线同步（见 §3、§4）。

**用户反算不闭合（如实记录，不附和“正好 12 月”）**：

- 81.1528 ÷ 32.6667 = 2.4843（与用户一致）。
- 81.1528 ÷ 2.4068 = **33.72**，并非用户所称 33.667；要得 33.667，需 Z实 = 81.1528/33.667 = 2.4104。两个反算相差约 0.05 年（≈0.6 月），属手工/四舍五入误差，**不能据此判定“正好多 12 个月”**。真正的差异来自边界年权重误配，而非分母多 12 月。

## 2. Bug18：月指数 z>3 是否封顶、封顶在哪一层

### 2.1 官方依据（文号 + 原文）

**(1) 《北京市基本养老保险规定》（北京市人民政府令第 183 号，2006-12-14 公布，2007-01-01 施行）第十二条**（原文取自北京市政府官方 PDF，9 页本，第 3 页）：

> “城镇职工以本人上一年度月平均工资为缴费工资基数，按照 8% 的比例缴纳基本养老保险费，全额计入个人账户。
> **缴费工资基数低于本市上一年度职工月平均工资 60% 的，以本市上一年度职工月平均工资的 60% 作为缴费工资基数；超过本市上一年度职工月平均工资 300% 的部分，不计入缴费工资基数，不作为计发基本养老金的基数。**”

官方 PDF：`https://www.beijing.gov.cn/gongkai/zfxxgk/zc/gz/202112/W020211216544449063523.pdf`

**(2) 《国务院办公厅关于印发降低社会保险费率综合方案的通知》（国办发〔2019〕13 号）第三条**（中国政府网原文）：

> “……各省应以本省城镇非私营单位就业人员平均工资和城镇私营单位就业人员平均工资加权计算的全口径城镇单位就业人员平均工资，核定社保个人缴费基数上下限，合理降低部分参保人员和企业的社保缴费基数。……个体工商户和灵活就业人员……可在**本省全口径城镇单位就业人员平均工资的 60% 至 300% 之间选择适当的缴费基数**。”

原文：`https://www.gov.cn/zhengce/zhengceku/2019-04/04/content_5379629.htm`

**(3) 21 号文（京劳社养发〔2007〕21 号）附件一**定义了 `Z实指数=Σ(Xn/Cn-1)/N应缴`，但**只给指数公式，未逐字规定指数本身的上下限**。

### 2.2 官方口径的准确边界（不编造）

- 官方逐字规定的是**缴费基数（B月）受上年社平 60%~300% 核定**；超过 300% 的部分“不计入缴费工资基数，不作为计发基数”。
- 官方**没有**逐字出现“月指数 z 封顶为 3”或“Z实指数封顶为 3”的条文。
- 数学推论：**若 B月 已按 300% 上限核定，则 z = B月/C月 ≤ 3 恒成立，无需再封顶。** 本案引擎是“用户录入基数 → 直接算 z”，入口未强制 B月 ≤ 3×C月，因此在口径切换/录入高于实际核定基数时会出现 z>3。

> 因此“指数封顶”属于**工程建议/工程假设**：为与基数 300% 上限保持一致而在指数层补的约束，**不是官方逐字条文**。本备忘录不为此虚构文号。

### 2.3 封顶应加在哪一层（定稿）

**加在月指数层：`z月 = min(3, B月/C月)`，再汇总。不要只对最终 Z实 min(3,.**)。

理由：

1. **对象一致**：300% 上限约束的是每月缴费工资基数，进而每月指数，应按月生效。
2. **最终层封顶会漏判**：仅当总均值 >3 才触发。本案 Z实≈2.4 <3，最终层 min(3,Z实) **完全不起作用**，个别 >3 的高指数月会原样保留并继续抬高基础养老金 J基础（含 Z实）与过渡性养老金 G实（含 Z实），违背上限“不作为计发基数”的意图。
3. **勾稽自洽**：月层封顶后，年表 Z年、加权恒等式、Z实 全部由同一批已封顶月 z 汇总，展示与主汇总天然闭合。

### 2.4 2019 该月实算 z 与封顶影响

- 2019 缴费年：用户录年基数 293796、12 月 → B月 = **24483**；分母取 C2018（全口径）= **7855**。
- **z = 24483/7855 = 3.116868 → 年表/月明细显示 3.1169**（2019 年 12 个月相同）。

以当前 C 版 raw Σ月z = 942.74125、K=392 为基准：

| 方案 | 处理 | 分子变化 | Z实结果 |
|---|---|---|---|
| **月指数层 min(3,z)（定稿）** | 仅 2019 年 12 月被削 | 削减 12×(3.116868−3)=**1.4024**；新 Σ月z=941.3388 | **941.3388/392 = 2.40137 → 2.4014** |
| 仅最终 Z实 min(3,Z实) | Z实 2.4<3，不触发 | 0 | **2.4050（无变化），2019 高指数月保留 → 不可取** |

- 年表 2019：封顶前 Z年=3.1169；**月层封顶后 Z年=3.0000**。
- 对养老金的传导（定性）：Z实 2.4050→2.4014（−0.0036），将使 J基础、G实 等含 Z实 项小幅下降；本轮不跑业务代码，不给金额，由开发改后实算。

### 2.5 需要客户核对的不确定项（重要）

2019 z>3 很可能与**口径切换**有关：2019 起分母改用全口径 C2018=7855（此前为小口径，小口径社平更高/序列不同），分母口径跳变会放大指数。请核对：

- 2019 实际申报的缴费基数是否为社保系统按 300% 核定后的值（以缴费回执为准）。**若基数确已被核定，其真实 z 不应 >3**；出现 3.1169 说明（a）录入年基数高于实际核定基数，或（b）分母 7855 的口径与该基数申报口径不一致。
- 在客户确认前，月层 min(3,.) 作为安全兜底定稿；同时**保留封顶前原值字段（zRaw）供核对**。

### 2.6 附带发现（超出 Bug18 核心，记录但本轮不处理）

- 未来段语义是“每月 Z 值=0.6”，但 UI/引擎用**固定月基数 7162.2（=0.6×11937）**。分母 2026 起变为 12116 后，该段实际指数 = 7162.2/12116 = **0.5911 ≠ 0.6**。若“0.6”是目标指数，月基数应按各年分母动态换算（0.6×当年 C）。此项影响 §1.3 中 2026/2027+ 数值，列为**工程待决**，请产品/客户确认未来段是“固定金额”还是“固定指数”。

## 4. 给测试的验收点

**Bug17**

1. 窗口：`monthlyDetails` 首=2000-11、末=2033-06、长度 **392**；`N应缴=32.6667`；逐年 Σ windowMonths=392。
2. 勾稽恒等式：`Σ(Z年×windowMonths)/392` 与主汇总 `Z实` 容差 ≤0.0002（当前 C 版：封顶前 2.4049~2.4050；封顶后 2.4014）。
3. 边界年：2000 Z年=2.6747（window=2）、2033 Z年=0.5911（window=6），不得再出现被 12 月稀释的值。
4. 反向用例：直接把 34 行 Z年相加再除 32.6667 得到的 ~2.48 **不等于** Z实，且结果页有明确“需按应缴月加权”的提示。
5. 配置一致性：锁定 2026 年基数基线与 12116 分母后，`output-assert.js` 全绿；不再出现 2.4075/2.4068/2.4050 三种并存。

**Bug18**

6. 月指数封顶：构造任一月 B月/C月>3（如 2019 的 3.1169），断言 monthly `z=3.0`、`zCapped=true`、`zRaw=3.1169`；年表该年 Z年=3.0000。
7. 封顶层级：断言 Z实由**已封顶月 z**汇总（=2.4014），而非最终再 min；并验证“仅最终封顶”方案被否（zRaw>3 不允许原样进任何养老金分项）。
8. 传导：J基础、G实等含 Z实 的结果随 Z实 2.4050→2.4014 同步小幅变化；三分项与总额舍入规则（分项 round2、合计=分项展示值之和）不回归。
9. 未触发场景：所有月 zRaw≤3 时，z=zRaw、`zCapped=false`，结果与不封顶版本完全一致（不得误封顶）。
10. 断缴/缺分母月仍 z=0，封顶逻辑不影响其计入分母。

## 5. 官方口径 / 工程假设 / 不确定项 汇总

**【官方】**

- 缴费基数上下限 = 上年社平 60%~300%；超 300% 部分不计入缴费工资基数、不作为计发基数：**183 号令第十二条**（官方 PDF 已逐字核对）。
- 全口径口径核定基数上下限、灵活就业可在 60%~300% 间选择：**国办发〔2019〕13 号第三条**。
- Z实指数公式 `Σ(Xn/Cn-1)/N应缴`：**京劳社养发〔2007〕21 号附件一**。

**【工程假设】（非官方逐字条文）**

- 在**月指数层** `z=min(3,B月/C月)` 与基数 300% 上限对齐——官方未逐字写“指数封顶”，此为工程兜底；建议保留 zRaw。
- 2027 年起分母沿用最近官方值 12116（assumed，待逐年发布）。
- 未来段个人账户月滚动利率 1.5%/年折月复利（沿用既有工程模型）。

**【不确定 / 待客户确认】**

- 2026 年缴费基数基线：**286488 还是 287562**（材料不一致）。
- 2019 z>3 的真实成因：实际核定基数 vs 录入值、分母 7855 口径是否匹配；需核对 2019 缴费回执。
- 未来段“Z=0.6”指固定指数还是固定金额（当前固定 7162.2 在 12116 分母下只得 0.5911）。
- 各引擎/断言材料的历史中间态精确分母值（任务中“33.667/正好12月”无法由数据闭合，已在 §1.4 如实说明）。
