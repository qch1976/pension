## 2. Bug20：未来段缴费基数 7162.2 → 7270（MY1）/ 36348（MY2）

### 2.1 旧值 7162.2 的精确位置

grep `7162.2|35811|11937`（限定业务/测试代码）：

| 文件：行 | 代码 | 说明 |

| `autotest/output-assert.js:266` | `makeInput(1.0, 'enterprise'); // 未来段=11937 → …` | 不误封用例的注释 |

- **`calculator/pensionEngine.js`、`constants/policyData.js` 中没有 7162.2/7162、也没有未来段基数常量。** 引擎对未来段与历史段一视同仁，均取 `segments[].baseMonthly`。
- `pages/index/index.js` 无未来段默认基数（未来段由用户自己加 segment；第 378~380 行的 60%/100%/300% 快捷选择只改填充逻辑，不写死未来金额）。
- 结论：**7162.2 只存在于两份 autotest 的派生式 `z × 11937`**；"替换 7162.2"在代码层 = 替换这两个 `fb` 派生式，并由用户在输入页把未来段月基数改为 7270（真机录入，不属本轮代码改动）。

### 2.2 实算：新基数与月指数

2026 社平（指数 1.0 口径，全口径月平均工资）= **12116 元/月**：

```
0.6 档：12116 × 0.6 = 7269.6 → 取整 7270 元/月
MY1 未来段月指数 = 7270 / 12116 = 0.60003301… → 0.6000（与目标 0.6 差 3.3e-5，整数取整所致）
3.0 档：12116 × 3 = 36348 元/月
MY2 未来段月指数 = 36348 / 12116 = 3.00000000… 恰为 3
```

适用区间：**2026-09 ~ 2033-06，共 82 个月**（2026 年 4 月 + 2027~2032 共 72 月 + 2033 年 6 月；与 R储 月滚模型的 82 个月一致）。2027 年及以后分母沿用 12116（`denominatorFor` 无键回退最后键，标 `assumed`）——故该固定金额在全区间每月指数恒为上表值，无需逐年改基数。

### 2.3 精确替换规则（定稿）

**两份 autotest 的 `buildSegments(z, type)` 中：**

```js
// 旧（engine-assert.js:34 / output-assert.js:46）
var fb = Math.round(z * 11937 * 100) / 100;
// 新（Bug20：以目标 Z × 2026 社平12116 派生；MY1 整数取整）
var SOCIAL_2026 = 12116;
var fb = z === 0.6 ? 7270 : Math.round(z * SOCIAL_2026); // 0.6→7270；3→36348
```

（若后续有其他 z 值，统一规则 `fb = Math.round(z * 12116)`；0.6 档因官方/业务按元取整明确用 7270。）

- 未来段 segment 本身不变：`{ type: type, startYM:'2026-09', endYM:'2033-06', baseMonthly: fb }`。
- 两份文件头部"锁定基线"注释同步改为："未来段固定 7270/36348（=目标Z×12116），2026 起分母 12116"。
- `output-assert.js:266` 不误封用例的 `makeInput(1.0,'enterprise')` 派生出的未来基数变为 12116（z=1，zRaw=1<3），用例语义不受影响，注释更新。
- **MY2 不改目标 3.0**：其未来段月基数由旧 35811（=3×11937）改为 **36348（=3×12116）**，月指数 2.9557→**恰好 3.0000**，与"目标 Z=3"的口径反而更严格一致。
- 架构建议：未来段不再维护任何固定金额常量，一律**由"目标月指数 Z × 退休前最近官方社平"派生**（本年即 12116）；这样官方每年发布新社平后只需更新分母表。该建议为**工程假设**（官方对灵活就业只规定可在 60%~300% 间选基数，未规定本小程序的派生方式）。

## 3. Bug21：年度账回到官方字面年值法（推翻 Bug14）

### 3.1 定稿公式

对每个日历年 n（年表行）：

```
B月   = 当月缴费基数（应缴窗口内）；窗口外月份不进入该年序列
z月   = min(3, B月 / C月)                 ← Bug18 月层封顶，先执行
Xn    = Σ_窗口内各月 B月                  （官方 X年 = 年度各月缴费工资基数之和；窗口外月为0/不存在）
C年   = 12 × C月                          （全年社平，不论该年实际缴几个月）

Z年(n) = Xn ÷ C年 = Σ_窗口内 z月 ÷ 12
       C月 缺失 → null（1992~1995 缺口行，展示"—"）
```

要点：

- **整年（windowMonths=12）：Z年 = Σ月z/12 = 月均，与 Bug14 口径完全相同，数值不回归。**
- **边界年 2000（仅 11、12 月，windowMonths=2）、2033（仅 1~6 月，windowMonths=6）：分子只含实际窗口月，分母仍是 12 个月 → 被"稀释"回 Bug14 之前的年值。**
- 月层封顶事实不变：2019 年 12 个月在进 Σ 之前已是 3。
- 舍入：聚合一律用未舍入月 z；Z年 round4 仅用于展示。

### 3.2 唯一代码改动点

`calculator/pensionEngine.js → buildAnnualIndexLedger()`，当前第 310~315 行附近：

```js
// 旧（Bug14 口径，当前服务器）
// BUG-14：非整年（windowMonths<12）按实际应缴月数折算月均口径，不再用12月分母稀释
var zYear = null;
if (cMonthly != null) {
  zYear = windowMonths === 0 ? 0 : round4(sumMonthZ / windowMonths);
}

// 新（Bug21：官方字面年值法）
var zYear = null;
if (cMonthly != null) {
  zYear = round4(sumMonthZ / 12);   // 窗口外月本就不在 sumMonthZ；windowMonths=0 时 sumMonthZ=0 → 0
}
```

- `sumMonthZ`、`xAnnual`、`windowMonths`、`paidMonths` 的累计**全部保留**（windowMonths 仍用于"应缴月/实缴月"两列与 K 核对）。
- ledger 行的 `partialYear: windowMonths>0 && windowMonths<12` **字段可保留**（CSV/数据审计可用），但**页面不再据此显示"非整年·月均"**（见 §4）。
- 函数头注释（第 263~267 行）按年值法改写，删除"BUG-14 修正""非整年按应缴月数折算"等描述。
- 主循环、`Z实 = sumZ/K`、`K=392`、`N应缴` **一律不动**。

### 3.3 恒等证明（实算，非推导口号）

年值法下，对窗口内每个日历年：`Z年_raw = Σ_该年窗口月 z / 12`。对 34 个窗口年（2000~2033）求和：

```
Σ34行 Z年_raw = Σ_34年 Σ_窗口月 z / 12 = (Σ_全部392月 z) / 12
Σ34行 ÷ N应缴 = (Σ392月 z / 12) ÷ (392/12) = Σ392月 z / 392 = Z实      ∎
```

node 实跑（目标配置，raw 值）：

| | MY1 | MY2 |
|---|---|---|
| 主汇总 Z实（Σ已封顶月 z /392） | **2.403235737666374** | **2.905269647962082** |
| Σ34行 raw Z年 ÷ N应缴 | **2.403235737666367** | **2.905269647962080** |
| 差 | 7e-15（浮点误差） | 2e-15 |
| Σ34行 **round4 行值** ÷ 32.6667 | 2.40322653 → 显示 **2.4032** | 2.90526429 → 显示 **2.9053** |
| Σ34行 round4 行值（直接相加） | **78.5054** | **94.9053** |

即：**34 行 Z年可以直接相加再除以 N应缴 32.6667，结果即主汇总 Z实**（用 raw 值严格恒等；用页面 round4 行值在 ±0.0001 内闭合，与现有显示精度一致）。

对照：Bug14 口径下的旧加权式 `Σ(Z年×windowMonths)/392` 在目标配置上得 MY1 2.3873、MY2 2.8709，**已不再等于 Z实，必须从页面/CSV 文案中移除**。

## 7. 官方口径 / 工程假设 / 不确定项

**【官方】（有文号/原文）**

- `Z实指数 = Σ(Xn/Cn−1) ÷ N应缴`，`Xn = 相应年度各月本人缴费工资基数之和`：**京劳社养发〔2007〕21 号附件一**（官方公式图）。本轮 Bug21 即回归该字面年项口径。
- 缴费基数 60%~300% 上下限：**北京市政府令 183 号第十二条**；灵活就业可在全口径社平 60%~300% 间选基数：**国办发〔2019〕13 号第三条**。
- 2026 社平/全口径月均 12116：按用户提供的权威输入（My-Case 口径）；小程序内 `policyData.fullCaliberMonthly[2025]=12116` 同源。

**【工程假设】（非官方逐字条文，代码注释/页面须标注）**

- 0.6 档月基数取整为 **7270 元**（7269.6 四舍五入到元），其月指数 0.60003 ≈ 0.6；MY2 36348 恰为 3。
- 未来段基数"由目标 Z × 12116 派生"为工程统一规则；官方只规定可选档位区间。
- **2027 年起分母沿用 12116（assumed，待逐年发布）**——故 7270 在 2027+ 的真实指数有待官方社平发布后复核；若未来社平偏离 12116，固定金额 7270 的实际指数将不再恰好 0.6（此时需按"目标 Z × 新年社平"重派生）。
- 月指数层 `z=min(3,…)`（Bug18）仍属工程兜底；未来段 1.5%/年折月复利模型沿用。

**【不确定 / 待确认】**

1. 12116 的官方发布件编号/直链本轮未独立取证（采用 My-Case 权威输入与既有 policyData 配置）；建议落地时在 spec 补官方通告链接。
2. 21 号文对"窗口边界年"字面只给年项公式、无专门问答；本轮按用户明确要求采用**官方字面年值法**（Bug14 的月均法被正式推翻），语义上边界年 Z年是"被全年稀释的年值"，勾稽上严格闭合。
3. 窗口内断缴月计分母（T-05）仍待经办复核；本案无断缴月，无数值影响。
4. Bug17 备忘录中"未来段固定金额 vs 固定指数"的待决项，本轮由用户定稿为：**金额固定 7270，工程上按目标 Z×社平派生**（MY2 同理 36348）。
