## 1. Bug23：应缴窗口规则定稿（口径B）

### 1.1 现行逻辑取证

`calculator/pensionEngine.js`：

```js
var DEEMED_END_IDX = D.toIndex('1992-09');
var PHYS_BUILD_START_IDX = D.toIndex(P.deemedContributionStart); // 恒定 1992-10

function insuredWindowStart(input) {
  var def = PHYS_BUILD_START_IDX;                       // ① 默认物理建账起点
  if (input.doc31Eligible === true && input.enterpriseInsuredYM &&
      /^\d{4}-\d{2}$/.test(input.enterpriseInsuredYM)) {
    var idx = D.toIndex(input.enterpriseInsuredYM);
    if (idx >= def) return idx;                        // ② 31号文人员：批准参保月
  }
  return def;                                          // ③ 其他所有人：1992-10（硬编码）
}
```

- `buildMonthMap` 的**物理截断仍恒为 1992-10**（早于 1992-10 的段不建账，E-02 提示）——与窗口起点是两个参数，不混用。
- 主汇总 `Z实 = sumZ / K`，`K = 窗口月总数（窗口起点 → 退休前一月）`。

### 1.2 新规则（定稿，V1.7 §2.1 / §4.5 以此为准）

```
【窗口终点】退休前一月（不变）。

【窗口起点 insuredWindowStart(input)】
  ① doc31Eligible=true（31号文人员）：保留现有逻辑
       enterpriseInsuredYM 合法且 ≥1992-10 → 起点 = enterpriseInsuredYM（批准参保月）
       否则回退 1992-10（并由既有校验提示）
  ② doc31Eligible≠true（普通企业职工/灵活就业/新人）：
       workStartYM 合法（YYYY-MM）且 >1992-10 → 起点 = workStartYM（参加工作月）
       否则 → 起点 = 1992-10
    即  窗口起点 = max(1992-10, workStartYM)
```

**边界逐条写清：**

| # | 情形 | 窗口起点 | 说明 |
|---|---|---|---|
| a | 中人，1992-10 **前**参工（如 MY1/2 的 workStartYM=1995-07…注：MY1/2 实走 31 号文分支；一般老中人如 1985-07 参工） | **1992-10** | max 取建账月；参工→1992-09 的连续工龄走视同（N同），不进 Z实分母 |
| b | 中人，1992-10 **后**、1998-07 前参工（如 1995-07 普通企业中人） | **workStartYM** | 参工即应缴；参工前未在业月零指数但不再计分母 |
| c | 新人，1998-07 后参工（MY3/4 = 2003-09） | **workStartYM** | 本案核心：窗口 2003-09 起，K=334/394 |
| d | workStartYM 缺失/非法（非 31 号文人员） | **1992-10** | 兜底；由既有 warnings 提示补录，不新增硬错误 |
| e | workStartYM 晚于退休月 | validate 已拦截（既有逻辑） | — |
| f | 31 号文人员 | enterpriseInsuredYM（现有逻辑，**不改**） | 新分支显式排除 doc31 人员 |

**"首账号月与参工月不一致时以哪个为准"——规则与理由：**

- 本产品**只有一个用户录入锚点 `workStartYM`（参加工作年月）**，不单独采集"首次建立养老账号月"（输入页/引擎均无该字段；MyWife-Case 中首账号=参工月=2003-09，仅文案意义）。
- 定稿：**窗口起点只认 `workStartYM`**。理由：① 应缴义务随劳动关系/参工开始，"首账号"是社保经办的建账动作时点，实务中可能因单位补办、跨制度转入而晚于参工，以它为起点会漏计真实应缴月；② 31 号文人员的"批准参保月"已是独立字段 `enterpriseInsuredYM`，语义专门覆盖"参工但晚建账"情形，不与普通人员混用；③ 避免新增录入项扩大本轮范围。
- 若未来确有"参工月≠首账号月"的普通人员案例（经办要求按首账号截断），作为**未来工作**另开字段与规则，本轮不实现，spec 备注。

**窗口内断缴月（不变规则，明确保留）：**

- MY3/4 的 2005 年缴 7 月（缺 5 月）、2006 年缴 9 月（缺 3 月）：缺口月在窗口内 **z=0、仍计入 K**（T-05 北京口径）；年表中该两年 Z年 = Σ缴月 z ÷ 12（被全年分母稀释，见 §1.4）。
- 断缴月位置：案例只给年基数+月数，录入按连排（2005=01~07、2006=01~09）；年值法下缺口排月不影响 Z年/Z实金额，逐月断言以连排为准。

### 2.2 定稿：显式"有/无视同缴费年限"状态

**（1）数据模型（`inputPageModel.js`）**

```js
// userEntryPart 新增
hasDeemed: false,          // 是否有经认定的视同缴费年限（默认关）
deemedStartYM: '',         // 仅 hasDeemed=true 时可录
deemedEndYM: '',
```

- `buildInitialData / buildResetData` 均默认 `hasDeemed:false`、起止空（清空按钮后回到"无视同"）。
- 引擎输入映射：
  ```js
  deemedStartYM: d.hasDeemed ? (d.deemedStartYM || null) : null,
  deemedEndYM:   d.hasDeemed ? (d.deemedEndYM   || null) : null,
  ```
  即**无视同时 N同/deemedMonths 按 0**——保持现行"不使用该字段"行为，引擎计算逻辑零改动。
- doc31=true 时的强制校验改为：`hasDeemed=true` 且起止合法（开关与 31 号文身份联动提示，但不自动替用户拨开关）。

**（2）交互（`index.wxml/js`）**

- ②卡标题下新增一行开关（沿用现有 `.opt` 两段式样式，与"性别/31号文"一致的视觉语言）：

```text
是否有经认定的视同缴费年限？   [ 无视同缴费年限 ] [ 有视同缴费年限 ]
```

- **关（默认）**：两个 picker 隐藏；行位展示灰字 **"无视同缴费年限（N同=0）"**；并立即把 `deemedStartYM/deemedEndYM` 置空（解决"删不掉"）。
- **开**：出现两个 picker（现有控件，占位文案保留但去掉具体案例值，见 §3）；可选值、可再关回；每次从开切到关都清空起止。
- **可反复切换/清除**：开→关→开不报错；关状态下点测算视同按 0；不设二次确认（操作可逆、无数据破坏——开关关只是隐藏并清空本案视同值，用户重新打开重选即可）。
- 建议在开状态下 picker 旁各放一个小字"清除"（点等同于仅清空该端；实际上直接关总开关即可，开发可选做，不强制）。

**（3）storage 迁移规则（不得强覆盖真实草稿、不得跨案残留假数据）**

`onLoad` 现有合并：`Object.assign(buildInitialData(P), saved, {calculating:false,errorMsg:''})`。定稿改为带迁移：

```js
var saved = wx.getStorageSync('pension_input_v1');
if (saved) {
  var base = Model.buildInitialData(P);
  var merged = Object.assign({}, base, saved, { calculating:false, errorMsg:'' });
  // 迁移：旧草稿无 hasDeemed 字段时，按"是否有非空起止"派生，避免凭空改变用户旧状态
  if (saved.hasDeemed == null) {
    merged.hasDeimed = !!(saved.deemedStartYM || saved.deemedEndYM);
  }
  // Bug22 核心：hasDeemed=false 时，强制视同起止不残留（清除旧案值）
  if (!merged.hasDeemed) { merged.deemedStartYM = ''; merged.deemedEndYM = ''; }
  this.setData(merged);
}
```

要点：

- **不强覆盖用户真实草稿**：所有其他字段沿用 saved；若旧草稿确有视同起止且无开关字段，迁移推定"有"并保留其值（用户真数据不丢）。
- **不得跨案残留默认假数据**：本产品视同字段默认从无写死值；残留只可能来自上一案草稿——一旦用户（或默认）处于"无视同"，起止一律清空。用户在 MY3/4 打开小程序时，若沿用上轮 MY1/2 草稿，迁移会把视同推定成"有"（因旧值非空）——**此时用户只需点一下"无视同"即清除**；这是对真实旧值最保守的处理，不擅自删除。
  - 备选（更激进，不采纳）：按 workStartYM 校验残留起止是否在参工月之后、在之前就自动清空——虽符合本案，但"参工月前的视同也可能真实存在（中人参工前工龄）"，自动清除有丢真数据风险，故不做自动判定，只做开关手动清除。
- storage key 可保持 `pension_input_v1`（结构向后兼容，仅增字段）；若开发选择升 `v2`，须做一次性读取迁移且不双写混用。

**（4）范围边界（明确不做）**

- **不实现"中人视同年限真正参与运算"的任何新逻辑**：当前引擎对有效视同（1992-09 前 → G同、1992-10~1998-06 → G实）已有实现，本轮仅修输入状态与清除；"视同年限在 MY 类新人案件中应否影响待遇"不适用（新人本应无视同）。
- 未来工作（spec 备注，不开工）：① 普通人员"首账号月≠参工月"的独立字段；② 视同区间与参工月逻辑矛盾（如起止早于参工）的主动 warning 增强（现行引擎静默按交集0处理，本轮保留，可加一条软提示，见 §5 验收点，非强制）。
